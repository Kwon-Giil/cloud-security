# Juice Shop 파일 탐색 및 쿠폰 변조 시도

**Date:** 2026-09-19
**Category:** Web Security / Hands-on

## 1. 학습 목표

Juice Shop에서 웹 애플리케이션에 노출된 파일을 탐색 후 백업 파일을 다운로드 받은 뒤, 백업 파일에 포함된 데이터를 분석하여 쿠폰 생성 규칙 추론

또한 추론한 규칙을 바탕으로 쿠폰 변조를 시도하고, 예상과 다른 결과가 발생했을 때 그 원인을 단계적으로 확인.

---

## 2. 학습 내용

### 2.1 웹 애플리케이션의 노출 파일 탐색

Juice Shop의 URL 경로를 탐색하면서 일반적인 화면에서 직접 노출되지 않는 파일 및 디렉토리를 확인.

`./ftp` 경로에 접근하여 애플리케이션과 관련된 백업 파일을 확인하고, 파일 확장자를 변경하여 내부 내용을 확인함.

이를 통해 웹 애플리케이션에서 현재 서비스 기능뿐만 아니라 **백업 파일, 이전 데이터, 테스트용 파일 등이 외부에 노출될 경우 보안 문제가 발생할 수 있음**을 확인함.

### 2.2 쿠폰 백업 파일 분석

ftp 경로에서 백업 파일을 다운로드 받은 뒤 쿠폰과 관련된 데이터를 확인하고, 쿠폰 번호의 형태와 반복되는 문자열 패턴을 비교.

이를 바탕으로 쿠폰 번호가 단순한 난수 형태가 아니라 일정한 규칙 또는 데이터 변환 과정을 거쳐 생성될 가능성을 추론해 냄.

### 2.3 Z85 인코딩/디코딩

쿠폰 데이터에 사용된 것으로 보이는 Z85 인코딩을 확인하고, 인코딩된 문자열을 디코딩하여 원본 데이터 분석.

이후 원하는 조합의 값을 직접 생성하고 다시 Z85 방식으로 인코딩하여 새로운 쿠폰 번호를 만들 수 있는지 시도.

## 4. Troubleshooting

### 4.1 기존 쿠폰 문자열의 일부만 변경

기존 쿠폰 번호들의 패턴을 확인한 후 전체적인 문자열 구조는 유지하고 일부 문자만 변경하여 새로운 쿠폰 번호 생성 시도

변조한 쿠폰을 적용했지만 정상적인 쿠폰으로 인정되지 않았음.

이를 통해 **문자열의 겉보기 규칙을 파악하는 것만으로 실제 유효한 쿠폰을 생성할 수 있는 것은 아닐 수 있음**을 확인함.

### 4.2 Z85를 이용한 원하는 값 재생성

쿠폰 데이터의 인코딩 방식을 확인하기 위해 Z85 디코딩을 수행한 뒤, 원하는 조합의 데이터를 직접 만들고 다시 Z85로 인코딩함.

예를 들어 `jan28-99`와 같이 원하는 값을 생성한 뒤 해당 문자열을 인코딩하여 새로운 쿠폰 번호를 만들어 검증함.

그러나 역시 정상적인 쿠폰으로 인정되지 않았음.

이를 통해 **데이터의 인코딩 방식을 알고 있더라도 그것만으로 애플리케이션에서 유효한 값을 생성할 수 있다고 보장할 수 없다는 점**을 확인함.

현재 실습에서는 쿠폰 생성 및 검증 과정의 정확한 내부 로직까지 확인하지 않았기 때문에, 변조한 쿠폰이 거부된 구체적인 원인 추가 분석 필요.

## 5. 오늘 배운 점

오늘 실습을 통해 웹 애플리케이션을 분석할 때 단순히 화면에 표시되는 기능만 확인하는 것이 아니라, **노출된 파일과 데이터까지 탐색 범위를 확장할 필요가 있다**는 점을 확인함.

또한 다음과 같은 분석 흐름을 직접 경험함.

```text
웹 경로 탐색
   ↓
노출된 파일 발견
   ↓
백업 데이터 확인
   ↓
문자열 패턴 분석
   ↓
인코딩 방식 확인
   ↓
생성 규칙 추론
   ↓
가설별 변조 시도
   ↓
유효성 검증
```

특히 쿠폰 변조 과정에서 두 가지 방식으로 접근했음에도 모두 실패하면서, **데이터의 형식이나 인코딩 규칙을 확인하는 것과 애플리케이션이 해당 데이터를 유효한 값으로 인정하는 것은 별개의 문제**라는 점을 이해함.

## 6. Key Takeaway

오늘은 Juice Shop의 `/ftp` 경로에서 백업 파일을 탐색하고, 쿠폰 데이터를 분석하여 생성 규칙을 추론한 뒤 실제 변조를 시도.

첫 번째로 기존 쿠폰 문자열의 패턴을 유지하면서 일부 값을 변경했고, 두 번째로 Z85 디코딩/인코딩을 활용하여 원하는 데이터를 직접 생성해 봄.

두 방식 모두 최종적으로 유효한 쿠폰으로 인정되지 않았지만, 이를 통해 **웹 보안 테스트에서는 단순히 데이터 형식이나 규칙을 알아내는 것에서 끝나는 것이 아니라, 실제 애플리케이션의 생성 및 검증 과정을 함께 분석해야 한다는 점**을 확인함.

또한 공격이 성공하지 않더라도 **가설을 세우고 직접 검증한 뒤 실패 원인을 좁혀가는 과정 자체가 보안 분석의 중요한 학습 과정**임을 경험함.
