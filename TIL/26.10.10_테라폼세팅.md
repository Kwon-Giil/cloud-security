# Terraform 설치 및 AWS VPC 생성·삭제 실습

**Date:** 2026-10-10  
**Category:** Cloud / AWS / Terraform / IaC

## 1. 학습 목표

Terraform을 설치하고 AWS Provider를 초기화하여 AWS 리소스를 코드로 관리하는 기본 흐름을 익힘.

`terraform init`, `terraform plan`, `terraform apply`를 실행하여 VPC 생성 계획과 실제 적용 과정 확인. 또한 AWS Organizations의 Service Control Policy(SCP)에 의해 리소스 생성이 거부되는 상황을 확인하고, 리소스 생성 후 `terraform destroy`로 제거하는 과정까지 경험.

---

## 2. 학습 내용

### 2.1 AWS CLI 설치 및 설정

먼저 WSL 환경에서 AWS CLI를 사용하려 했으나 설치되어 있지 않았음.

```bash
aws sts get-caller-identity
```

명령 실행 시 `aws: command not found`가 발생하여 AWS CLI 설치.

```bash
sudo apt update && sudo apt install awscli -y
```

설치 후 버전을 확인하고 AWS CLI 설정 진행.

```bash
aws --version
aws configure
```

AWS CLI를 통해 Terraform에서 사용할 AWS 인증 환경 준비 완료. 인증정보 자체는 TIL에 기록하지 않았음.

### 2.2 Terraform 설치

Terraform도 설치되어 있지 않아 처음에는 `terraform init`을 실행할 수 없었음.

Snap을 이용한 설치를 시도했으나 Classic Confinement에 대한 추가 확인 필요. 이후 HashiCorp 공식 배포 페이지에서 Linux용 Terraform 1.9.8 바이너리를 직접 내려받아 설치.

```bash
sudo apt update && sudo apt install -y wget unzip

wget https://releases.hashicorp.com/terraform/1.9.8/terraform_1.9.8_linux_amd64.zip

unzip terraform_1.9.8_linux_amd64.zip

sudo mv terraform /usr/local/bin/

terraform -v
```

설치 후 `terraform -v`를 실행하여 Terraform 1.9.8이 정상적으로 실행 확인.

### 2.3 Terraform 초기화

실습을 위한 작업 디렉터리를 생성.

```bash
mkdir terraform-aws-lab && cd terraform-aws-lab
```

이후 Terraform 초기화 진행.

```bash
terraform init
```

초기화 과정에서 AWS Provider `v5.100.0`이 설치되고 `.terraform.lock.hcl` 파일 생성 완료.

이를 통해 Terraform이 AWS 리소스를 관리하기 위한 Provider를 준비하고, 사용할 Provider 버전을 기록하는 기본 과정 확인.

### 2.4 Terraform Plan

다음 명령으로 실제 리소스를 생성하기 전에 실행 계획 확인.

```bash
terraform plan
```

계획에는 다음과 같은 VPC 생성 작업 표시.

| 항목 | 설정 |
|---|---|
| Terraform 리소스 | `aws_vpc.my_vpc` |
| 리소스 유형 | AWS VPC |
| CIDR 블록 | `10.0.0.0/16` |
| Name 태그 | `lab-vpc` |
| 예상 작업 | 리소스 1개 생성, 변경 0개, 삭제 0개 |

`terraform plan`은 실제 리소스를 생성하기 전에 어떤 변경이 이루어질지 확인하는 단계라는 점 경험.

### 2.5 Terraform Apply 및 VPC 생성

계획을 확인한 뒤 다음 명령으로 실제 적용 시도.

```bash
terraform apply
```

실행 중 AWS Organizations의 Service Control Policy(SCP)에 의한 명시적 거부 오류 발생.

오류 메시지의 주요 내용은 다음과 같았음.

```text
UnauthorizedOperation
You are not authorized to perform: ec2:CreateVpc

with an explicit deny in a service control policy
```

이는 Terraform 코드의 실행 계획을 생성하는 데에는 성공했지만, AWS에서 VPC 생성 API를 수행하는 단계에서 권한이 차단되었음을 의미.

이후 정책 적용 상태와 계정 구성을 확인하는 과정을 거쳤으며, 재시도 후에는 VPC가 정상적으로 생성 확인.

### 2.6 Terraform Destroy 및 정리

VPC 생성이 성공한 뒤 다음 명령으로 Terraform이 관리하는 리소스를 제거.

```bash
terraform destroy
```

삭제 계획을 확인하고 승인한 결과, 생성했던 VPC가 정상적으로 제거 확인.

```text
Destroy complete! Resources: 1 destroyed.
```

이후 실습 디렉터리에서 Terraform의 로컬 상태 및 초기화 파일을 정리.

```bash
rm -rf .terraform .terraform.lock.hcl terraform.tfstate terraform.tfstate.backup
```

이번 실습에서는 리소스를 먼저 삭제한 뒤 관련 로컬 파일 정리.

## 4. Troubleshooting

### 4.1 AWS CLI가 설치되어 있지 않은 문제

처음 `aws sts get-caller-identity`를 실행했으나 다음 오류 발생.

```text
Command 'aws' not found
```

AWS CLI가 설치되어 있지 않은 것을 확인하고 다음 명령으로 설치.

```bash
sudo apt update && sudo apt install awscli -y
```

설치 후 버전을 확인하고 AWS CLI 설정을 진행.

### 4.2 Terraform 설치 및 실행 문제

처음 Terraform 명령을 실행했을 때 다음과 같이 설치되어 있지 않다는 메시지 출력.

```text
Command 'terraform' not found
```

Snap 설치를 시도했으나 Classic Confinement에 대한 추가 확인이 필요했음. 해당 방식으로 설치를 진행하지 않고, 공식 배포 ZIP 파일을 내려받아 바이너리를 `/usr/local/bin/`에 배치하는 방식으로 설치.

이후 `terraform -v`에서 정상적으로 버전이 표시 확인.

### 4.3 SCP에 의한 VPC 생성 거부

`terraform apply` 실행 시 AWS API가 다음 작업 거부.

```text
ec2:CreateVpc
explicit deny in a service control policy
```

오류 메시지에는 AWS Organizations의 SCP 정책 ID가 표시되었음. 이는 IAM 사용자에게 부여된 권한만으로는 작업을 허용할 수 없고, 상위 수준의 정책에서 명시적으로 거부하고 있음을 의미.

provider 스크립트 내 리전을 서울에서 미국 동부(`us-east-1`)로 변경하여 재시도했지만 동일한 SCP 거부 오류가 발생했다. 따라서 리전 변경만으로는 문제가 해결되지 않는 것을 확인.

또한 다음 명령으로 정책 정보를 확인하려 했으나 권한 부족 오류가 발생.

```bash
aws organizations describe-policy --policy-id <정책 ID>
```

오류 메시지를 통해 IAM 사용자의 권한뿐만 아니라 AWS Organizations의 서비스 제어 정책(Service Control Policy, SCP) 에 의해서도 작업이 거부될 수 있음을 확인.

처음에는 BudgetsSpendLimitDenyNewWorkloads 정책을 의심했으나, 해당 정책에는 연결된 대상이 없는 것을 확인.

이후 AdvancedModeRegionRestrictionSecurityControlPolicy의 JSON 설정을 확인한 결과, 실습에 사용할 서울 리전(ap-northeast-2)이 허용 리전에 포함되어 있지 않았음.

해당 정책의 JSON 설정을 수정하여 서울 리전만 허용하도록 변경한 뒤 terraform apply를 다시 실행. 이후 VPC 생성이 정상적으로 진행되는 것을 확인.

이번 문제를 통해 다음 사항을 확인함.

- IAM 사용자에게 필요한 권한이 있더라도 SCP에서 명시적으로 거부하면 작업이 차단될 수 있음.

- 권한 오류가 발생하면 IAM 정책만 확인할 것이 아니라 적용 중인 SCP의 허용·거부 조건도 확인해야 함.

- 리전 제한 정책을 변경할 때는 실습에 필요한 리전이 허용 목록에 포함되어 있는지 확인해야 함.

## 5. Assessment

다음 항목을 직접 수행하고 결과를 확인.

- AWS CLI와 Terraform을 설치하고 실행할 수 있는가?
- `terraform init`으로 AWS Provider를 초기화할 수 있는가?
- `terraform plan`으로 리소스 생성 계획을 확인할 수 있는가?
- `terraform apply`로 VPC 생성을 시도하고 AWS의 권한 오류를 확인할 수 있는가?
- `terraform destroy`로 생성한 VPC를 제거할 수 있는가?

최종적으로 VPC 생성과 삭제에 성공. 다만 SCP에 의한 명시적 거부가 발생했던 정확한 원인과 이후 허용된 이유는 추가 확인 필요한 상태.

## 6. 오늘 배운 점

오늘은 AWS CLI와 Terraform을 설치하고, Terraform Provider 초기화부터 리소스 생성 계획 수립, 실제 적용, 리소스 삭제까지의 기본 흐름 경험.

특히 `terraform plan`에서 생성 계획이 정상적으로 표시되더라도 실제 AWS API 호출 단계에서 권한 오류가 발생할 수 있다는 점을 확인.

또한 IAM 사용자 권한 외에도 AWS Organizations의 SCP가 리소스 생성을 제한할 수 있으며, 명시적 거부가 적용된 경우 단순히 IAM 권한을 추가하거나 리전을 바꾸는 것만으로는 문제가 해결되지 않을 수 있다는 점을 배웠음.

마지막으로 Terraform을 사용해 리소스를 생성하는 것뿐 아니라 실습 후 삭제하고, 로컬 상태 파일을 정리하는 과정도 인프라 실습의 일부라는 점을 경험함.

## 7. Key Takeaway

오늘은 다음 흐름을 직접 경험함.

```text
AWS CLI 설치 및 설정
        ↓
Terraform 설치
        ↓
AWS Provider 초기화
        ↓
terraform plan
        ↓
terraform apply
        ↓
SCP에 의한 명시적 거부 확인
        ↓
재시도 후 VPC 생성 성공
        ↓
terraform destroy
        ↓
로컬 상태 및 초기화 파일 정리
```

이번 실습의 핵심은 **Terraform으로 인프라를 선언하고 실행하는 기본 과정과, AWS 권한 정책이 실제 리소스 생성에 영향을 미치는 구조를 경험함**.

다만 SCP 오류의 정확한 해소 원인은 확인되지 않았으므로, 이후 비슷한 문제가 발생하면 정책 이름만 보고 임의로 분리하기보다 실제 적용 대상과 계정 구조를 먼저 확인해야 함.
