# Terraform Remote Backend 및 AWS 인프라 코드 작성

**Date:** 2026-10-13  
**Category:** Cloud / AWS / Terraform / Infrastructure as Code

## 1. 학습 목표

Terraform의 Remote Backend를 이용해 상태 파일을 원격으로 관리하는 구성을 작성하고, AWS 네트워크와 컴퓨팅 리소스를 코드로 정의하는 방법 학습.

S3와 DynamoDB를 이용한 상태 관리 구성을 준비하고, VPC·서브넷·라우팅·보안 그룹을 구성한 뒤 퍼블릭 및 프라이빗 서브넷에 EC2 인스턴스를 배치하는 코드 작성.

마지막으로 `terraform plan`과 `terraform apply`를 실행하여 작성한 코드의 계획을 검증하고 실제 AWS 리소스 생성.

---

## 2. 학습 내용

### 2.1 Terraform Remote Backend 구성

Terraform의 상태 파일인 `terraform.tfstate`를 로컬이 아닌 S3에 저장하고, DynamoDB를 이용해 상태 잠금을 관리하도록 Backend 설정을 작성.

`provider.tf`에 다음과 같이 설정.

```hcl
terraform {
  required_version = ">= 1.0.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }

  backend "s3" {
    bucket         = "my-terraform-state-bucket-2026-giil"
    key            = "vpc/terraform.tfstate"
    region         = "ap-northeast-2"
    dynamodb_table = "terraform-lock"
    encrypt        = true
  }
}
```

주요 설정의 의미는 다음과 같음.

| 설정 | 의미 |
|---|---|
| `bucket` | Terraform 상태 파일을 저장할 S3 버킷 |
| `key` | S3 버킷 내부에서 상태 파일을 저장할 경로 |
| `region` | Backend가 위치한 AWS 리전 |
| `dynamodb_table` | Terraform 상태 잠금에 사용할 DynamoDB 테이블 |
| `encrypt` | S3에 저장되는 상태 파일의 서버 측 암호화 활성화 |

이를 통해 Terraform 상태를 원격으로 관리하고, 여러 실행 주체가 동일한 상태를 동시에 변경하는 상황을 방지하기 위한 잠금 구조 구성.

단, 현재 `provider.tf`는 기존 S3 버킷과 DynamoDB 테이블을 참조하는 Backend 설정이며, 해당 버킷과 테이블을 생성하는 리소스 코드는 포함하지 않음.

### 2.2 AWS 네트워크 인프라 코드 작성

`main.tf`에 EC2가 배치될 네트워크 환경과 보안 구성 작성.

전체 구성은 다음과 같음.

```text
VPC
 ├─ Internet Gateway
 │
 ├─ Public Subnet (AZ 1)
 │    └─ Public EC2
 │
 ├─ Public Subnet (AZ 2)
 │
 ├─ NAT Gateway + Elastic IP
 │    └─ Private Subnet의 외부 통신 경로
 │
 ├─ Private Subnet (AZ 1)
 │    └─ Private EC2
 │
 └─ Private Subnet (AZ 2)
```

Terraform 코드에서는 가용 영역 목록을 조회하고, 변수로 전달받은 CIDR 범위를 이용해 퍼블릭 및 프라이빗 서브넷을 생성하도록 구성.

퍼블릭 서브넷은 Internet Gateway를 통한 외부 통신 경로를 사용하고, 프라이빗 서브넷은 NAT Gateway를 통해 외부로 나가는 통신을 수행하도록 라우팅 테이블 구성.

### 2.3 보안 그룹 설정

웹 서버용 보안 그룹과 프라이빗 내부 서버용 보안 그룹 분리.

| 보안 그룹 | 주요 설정 |
|---|---|
| `web_sg` | TCP 80(HTTP), TCP 22(SSH) 인바운드 허용 |
| `private_db_sg` | `web_sg`를 출발지로 하는 TCP 3306 인바운드 허용 |

웹 서버는 외부 요청을 받을 수 있도록 설정하고, 프라이빗 서버는 웹 서버 보안 그룹을 통한 접근만 허용하도록 구성.

다만 현재 웹 서버 보안 그룹은 실습용으로 SSH 22번 포트를 `0.0.0.0/0`에 개방하도록 작성되어 있다. 이는 임시 설정이며, 다음 단계에서 접속 원본 IP를 본인 IP 대역으로 제한하거나 SSM Session Manager로 전환하여 22번 포트 자체를 닫는 방향으로 개선 예정.

또한 TCP 3306 규칙은 당초 DB 연결을 고려해 추가했으나, 현재 코드에는 RDS나 MariaDB 설치 구성이 포함되어 있지 않아 실제로 사용되지 않는 규칙이다. 최소 권한 원칙에 따라 해당 규칙은 제거하고, 이후 RDS를 실제로 구성하는 시점에 다시 추가 예정.

### 2.4 EC2 배치 코드 작성

두 종류의 EC2 인스턴스를 생성하도록 코드 작성.

| 인스턴스 | 배치 위치 | 주요 설정 |
|---|---|---|
| `public_web` | 첫 번째 퍼블릭 서브넷 | `t3.micro`, 퍼블릭 IP 연결 |
| `private_app` | 첫 번째 프라이빗 서브넷 | `t3.micro`, 퍼블릭 IP 미할당 |

AMI 데이터 소스를 이용해 Amazon Linux 2023 이미지를 조회하도록 구성하고, 각 인스턴스에 맞는 서브넷과 보안 그룹 연결.

이를 통해 Terraform으로 인스턴스의 배치 위치와 네트워크 접근 구성을 코드로 정의하는 방법 확인.

### 2.5 Terraform Output 설정

`outputs.tf`에서는 이후 리소스 정보를 확인할 수 있도록 주요 값을 출력하도록 설정.

```hcl
output "vpc_id" {
  description = "The ID of the VPC"
  value       = aws_vpc.main.id
}
```

VPC ID뿐만 아니라 퍼블릭 서브넷 ID, 프라이빗 서브넷 ID, 웹 서버 보안 그룹 ID도 출력하도록 구성.

이를 통해 Terraform이 생성한 리소스의 주요 식별자를 확인하고 이후 실습에 활용할 수 있도록 준비.

| 확인 항목 | 결과 |

이번 실습에서는 Remote Backend 설정부터 네트워크·보안 그룹·EC2 배치까지 하나의 구성으로 이어지는 Terraform 코드를 작성하고, Plan과 Apply를 통해 실제로 AWS에 리소스를 생성하는 흐름을 경험.

다만 생성된 EC2 인스턴스 간 통신이나 NAT Gateway를 통한 외부 연결이 실제로 의도한 대로 동작하는지에 대한 검증은 아직 수행하지 못했음.

## 5. 오늘 배운 점

오늘은 Terraform의 S3 + DynamoDB Remote Backend 설정을 작성하고, VPC·서브넷·라우팅·보안 그룹·EC2 배치까지 이어지는 AWS 인프라 코드를 구성.

이를 통해 Terraform으로 개별 리소스뿐 아니라 네트워크와 컴퓨팅 환경을 하나의 구성으로 정의하고, Plan으로 계획을 검증한 뒤 Apply로 실제 AWS에 반영하는 전체 흐름을 경험했음.

특히 퍼블릭·프라이빗 서브넷으로 계층을 나누고, 보안 그룹을 역할별로 분리하여 접근을 제어하는 설계를 코드로 직접 표현해 본 것이 이번 실습의 핵심.

## 6. Key Takeaway

오늘은 다음 흐름을 경험함.

```text
S3 + DynamoDB Remote Backend 설정
              ↓
VPC 및 네트워크 구성 코드 작성
              ↓
보안 그룹 설정
              ↓
퍼블릭·프라이빗 EC2 배치 코드 작성
              ↓
Terraform Plan 완료
              ↓
Terraform Apply 완료
```

**Terraform으로 네트워크부터 컴퓨팅 리소스까지 하나의 구성으로 코드화하고, Plan과 Apply를 통해 실제 AWS 인프라로 반영하는 전체 사이클**을 경험했음.

아직 생성된 인프라의 실제 동작(인스턴스 간 통신, NAT Gateway를 통한 외부 연결 등)은 검증하지 않은 상태이며, 다음 실습에서 이를 확인 예정.

## 7. Next

Public EC2와 Private EC2에 샘플 컨테이너(Nginx)를 배포하여, 지금까지 작성한 네트워크·보안 그룹 구성이 실제로 의도한 대로 동작하는지 검증 예정.

- Private EC2는 퍼블릭 IP가 없어 외부에서 직접 접속할 수 없으므로, Public EC2를 경유하는 Bastion 방식 또는 SSM Session Manager 중 하나로 접속 경로를 먼저 구성.
- Public EC2: Docker 설치 후 Nginx 컨테이너 실행 → 외부에서 80번 포트로 접속되는지 확인 (`web_sg`의 HTTP 인바운드 규칙 검증)
- Private EC2: 위에서 구성한 경로로 접속하여 Docker 설치 후 이미지를 pull 받을 수 있는지 확인 (NAT Gateway를 통한 외부 통신 경로 검증)
- 두 인스턴스 간 접근이 보안 그룹 설정대로 제한되는지(예: Private DB 보안 그룹이 Web 보안 그룹을 통한 접근만 허용하는지) 함께 점검

검증이 끝나면, 비용이 발생하는 리소스(NAT Gateway, Elastic IP 등) 중 더 이상 필요 없는 것은 `terraform destroy`로 정리하고, 이후 애플리케이션 배포 및 CI/CD 연동 실습으로 확장 예정.
